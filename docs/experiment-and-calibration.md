# 实验与校准方案

## 范围

本方案验证的是：**AI 编码代理在完成软件工程任务时，能否减少低价值测试生成与重复执行，同时保持缺陷发现能力。**

它不研究 LLM 模型基准测试、模型能力评测抽样或在线 A/B 流量分配。若目标转为减少模型评测次数，需要另行设计统计功效、样本代表性和模型排名稳定性实验。

## 待验证假设

1. 分层验证能降低编辑回路中的测试执行次数和等待时间。
2. affected-test selection 能保留大部分相关失败信号，并由提交后全量验证承担剩余风险。
3. 明确的停止规则能减少同一失败的重复执行、无归因修复和测试代码扩张。
4. 测试文件数、测试代码比例和 90 秒预算只能作为初始先验，不能在没有仓库数据时成为永久门禁。

## Pilot 仓库

首选本地 `maka-agent`，原因如下：

- TypeScript/npm workspaces monorepo，包含桌面端、运行时、存储、CLI 和 UI 等不同风险层级。
- 已提供 `typecheck`、`test:fast`、`test`、`test:full` 和 workspace 级测试入口。
- 同时存在快速验证、构建后测试和外部依赖/E2E 场景，适合验证分层策略。

正式实验必须从干净提交创建独立 worktree，不使用当前包含用户改动的工作区。

## 实验阶段

### 0. 基线

- 至少采集 30 个已完成任务，覆盖 `off`、`smoke`、`standard`、`thorough` 四档风险。
- 记录任务类型、变更文件、生产代码行数、测试代码行数、所有验证命令、耗时、退出码和重试原因。
- 保留完整测试结果作为 oracle，区分新失败、既有失败、环境失败和 flaky 失败。

30 个任务只用于发现数量级和明显问题，不足以证明安全性；样本应持续扩充，直到主要指标的区间稳定。

### 1. Shadow 模式

- 策略只给出推荐命令、预算告警和 fallback，不阻断 Agent。
- 同时记录“策略本来会选择什么”和“Agent 实际执行了什么”。
- 每个任务结束后异步运行完整相关检查，对比策略是否漏掉真实失败。
- 修正错误映射和预算阈值后，才进入强制阶段。

### 2. 有限强制

- 只拦截无目标的全量测试、等价命令的第三次即时执行和无法解析的高成本命令。
- `thorough` 任务不受低风险预算降级；未知变更必须扩大验证范围。
- 新规则先在非 required CI job 中运行，连续稳定后再升级门禁。

## 指标

### 效率指标

| 指标 | 定义 |
|---|---|
| 即时测试耗时 | 从首次编辑到任务交付期间测试命令的累计 wall time |
| 测试执行次数 | 规范化后不同/重复测试命令的次数 |
| 验证工具调用数 | lint、typecheck、build、test、E2E 等调用总数 |
| 测试扩张比 | 新增测试代码行 / 新增生产代码行；只作异常信号 |
| 重复失败率 | 相同失败在没有有效生产代码变更时再次出现的比例 |
| 首次归因时间 | 首次失败到被分类为代码/测试/环境/flaky 的时间 |

### 安全指标

| 指标 | 定义 |
|---|---|
| affected failure recall | 选中测试捕获的新失败 / oracle 完整检查捕获的新失败 |
| post-merge escape rate | 快速层未发现、在合并后或发布前发现的缺陷比例 |
| 高风险验证完成率 | `thorough` 任务完成规定集成/契约/E2E 的比例 |
| 未识别 fallback 率 | 无法可靠映射的变更是否全部升级到保守验证 |
| flaky 重试率 | 第二次运行结果不同的测试占比 |
| 回滚/返工率 | 因验证遗漏导致的回滚、补丁或额外 PR 比例 |

## 初始验收门槛

这些门槛是 pilot 的起始值，不是跨仓库标准：

- 即时测试耗时中位数至少下降 25%，P90 不因策略本身恶化。
- 规范化后的测试执行次数中位数至少下降 30%。
- `thorough` 任务的规定验证完成率保持 100%。
- 无法识别的变更 100% 触发保守 fallback。
- affected failure recall 目标不低于 95%；样本不足时保持 shadow 模式，不以单个百分比宣称安全。
- pilot 期间不得出现由策略降级直接造成的严重缺陷逃逸。

若效率达标但安全指标下降，结论是调整或拒绝当前策略，不允许用“测试更少”覆盖质量退化。

## 预算校准

`1` 个新增测试文件、`2` 次即时执行和 `90` 秒只作为第一轮观察值：

1. 按仓库和风险档分别统计耗时、执行次数、测试扩张比的 P50/P75/P90。
2. 测试文件数和代码比例只触发解释，不直接拒绝高价值回归测试。
3. 即时耗时上限取同档历史分布和团队反馈 SLA 的较小值。
4. 同一可归因失败允许一次修复后重跑；环境或 flaky 失败不消耗生产代码修复预算。
5. 每两周或累计 50 个任务后复核阈值，记录调整原因和前后指标。

## 保守 fallback 矩阵

| 变更类型 | 最低验证范围 |
|---|---|
| 纯文档/样式且不影响生成流程 | format/lint 或最小构建检查 |
| 叶子模块且存在可靠测试映射 | 目标测试 + 所属 workspace 检查 |
| 共享库、公共 API、跨 workspace 类型 | 所属 workspace + 直接依赖方测试 |
| 删除、移动、重命名 | 旧路径和新路径的映射并集 + 所属 workspace |
| lockfile、构建配置、测试配置、公共 fixture | 所有受影响 workspace；无法确定时全量 |
| schema、迁移、序列化、协议、权限、安全、支付、并发 | `thorough` + 人工确认 |
| 动态导入、反射、代码生成、未知扩展名 | 保守扩大到 workspace 或仓库全量 |
| 测试运行器、全局 setup、共享测试基础设施 | 所有使用该基础设施的测试组 |

任何“无法识别”都不能解释成“不需要测试”。

## 命令归一化与防绕过

预算不能基于原始命令字符串计数。实现时必须：

1. 用 shell parser 解析命令链，分别处理每个子命令；解析失败时按未知高成本命令处理。
2. 解析工作目录、package script、wrapper 和底层 runner，将等价入口映射为同一个 canonical command id。
3. 仅移除颜色、reporter 等非语义参数；目标文件、workspace、并发、shard、环境变量必须保留。
4. 对目标集合排序和去重，避免换序、别名或 wrapper 绕过重复执行计数。
5. 将 `npm test -- x`、workspace script 和直接调用 runner 的等价执行合并计数。
6. 高成本命令使用显式注册表和结构化元数据，不用 `grep test` 之类的字符串规则判断。

## Override 与验证账本

- 从低风险升级到更完整验证可以自动发生，但必须记录触发原因。
- 超出预算需要用户明确授权或命中高风险规则。
- `thorough` 降级只能由人工确认，Agent 不能自行以时间不足为理由跳过。
- override 不修改历史记录；账本同时保留原建议、覆盖决定和最终命令。

每个验证事件至少记录：

```json
{
  "schema_version": 1,
  "task_id": "task-identifier",
  "repository_commit": "git-sha",
  "policy_version": "policy-sha",
  "risk_level": "standard",
  "phase": "affected",
  "canonical_command_id": "npm:@maka/core:test:targets",
  "command": "npm --workspace @maka/core test -- settings.test.ts",
  "started_at": "ISO-8601",
  "duration_ms": 12000,
  "exit_code": 0,
  "failure_class": null,
  "override": null
}
```

## 结果判定

- **采用**：效率门槛达成，安全指标不下降，unknown fallback 和高风险验证均满足要求。
- **调整**：主要问题来自映射缺失、阈值不准或命令归一化错误，修正后回到 shadow 模式。
- **拒绝**：出现严重缺陷逃逸、持续降低 failure recall，或维护策略本身的成本高于节省的测试成本。
